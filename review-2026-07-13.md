## P1 — исправить до следующего релиза

### 1. UI и CLI используют разные реестры моделей для внешнего проекта

**Где:**

- `ui-backend/src/config.ts:28-36`
- `src/cli.ts:139-145`
- `ui-backend/src/process-manager.service.ts:93-117`

Backend Settings всегда читает и пишет `<ORCHESTRATOR_ROOT>/.orchestrator/models.yaml` и `.secrets`. При запуске с `--project /external/repo` CLI вместо этого загружает `/external/repo/.orchestrator/models.yaml` и `.secrets`. Следовательно, настройки и ключи, сохранённые в UI, не используются задачей над внешним проектом. Внешний проект получает новый дефолтный реестр, а health gate может вернуть `base_url/api_key missing`.

**Что исправить:** выбрать один явно задокументированный источник истины. Для текущей архитектуры логичнее хранить каталог моделей и секреты глобально в `ORCHESTRATOR_ROOT`, а target project использовать только для кода и project knowledge. Передавать путь реестра явно или отделить `configRoot`, `blackboardRoot` и `projectRoot` в API runner. Добавить integration-тест: изменить GLM key через backend, запустить внешний проект и проверить, что worker/health видит этот ключ.

### 2. Редактирование любой модели из UI отправляет невалидный DTO

**Где:**

- `ui-web/src/widgets/settings-models/AddModelModal.tsx:69-84`
- `ui-web/src/shared/api/index.ts:57-70`
- `ui-backend/src/models.dto.ts:88-96`

Форма переиспользует create-body и при update отправляет `id`, `kind`, а для API ещё `provider`. Backend update-схема строгая и принимает только `label`, `family`, `base_url`, `model`, `api_key`, поэтому запрос завершается 400. Точечная репродукция `modelUpdateSchema.safeParse(uiBody)` вернула `false`.

**Что исправить:** формировать отдельный update-body. Ещё лучше — экспортировать общий контракт или генерировать тип клиента из backend-схемы, чтобы frontend не объявлял более широкий `updateModel` вручную. Добавить API/component test на редактирование binary, Ollama и API-моделей.

### 3. Update API позволяет сделать сохранённую модель невалидной для её kind

**Где:**

- `ui-backend/src/models.dto.ts:88-96`
- `ui-backend/src/models.service.ts:225-237`

Update-схема не дискриминируется по текущему `kind`: она принимает `base_url` и `api_key` для binary-модели, а `model: ""` — для Ollama. Service слепо сливает patch с существующей записью и не валидирует итоговую модель. Репродукция подтвердила, что `{base_url: ...}`, `{api_key: ...}` и `{model: ""}` проходят `safeParse`.

**Что исправить:** после merge валидировать итоговую запись той же discriminated-union схемой без обязательного повторного API key; разрешать поля по текущему kind. Для Ollama запретить пустой `model`, для API валидировать provider/base URL, для binary запретить сетевые поля.

### 4. Workflow принимает опечатки в depends_on и дублирующиеся id

**Где:**

- `src/workflow.ts:59-126`
- `src/workflow.ts:164-174`
- `src/workflow.ts:242-260`

Schema не проверяет уникальность id и существование каждой зависимости. `topoLevels` и `orderLoopBody` специально считают неизвестную зависимость выполненной через `done.has(dep) || !byId.has(dep)`. В результате `depends_on: [typo]` запускает шаг немедленно вместо ошибки. Репродукция показала: schema принимает missing dependency и duplicate id; шаг с missing dependency попадает в первый уровень.

**Что исправить:** валидировать уникальность id и ссылки отдельно в `steps`, `loop.steps`, `post_steps`; определить допустимые межсекционные зависимости; удалить ветку `!byId.has(dep)` из сортировки. Добавить negative tests на typo, duplicate id, self-reference и ссылку между недопустимыми секциями.

### 5. Cache key не отражает реальное состояние кода

**Где:**

- `src/cache.ts:68-124`
- `src/runner.ts:369-377`
- `src/cache.integration.test.ts:67-92`

Есть две независимые причины stale cache:

1. Repo fingerprint включается только для `implement/refine/fix`; `plan/review/final` его игнорируют, хотя агенты запущены в worktree и могут читать файлы. Тест сейчас закрепляет неверное поведение: после нового commit ключ review остаётся прежним.
2. `dirtyFingerprint` — hash только `git status --porcelain`, без содержимого diff и untracked-файлов. Два разных изменения одного файла дают один ключ.

Дополнительно runner снимает fingerprint только при наличии `wt`, хотя read-only роль работает в integration cwd.

**Что исправить:** fingerprint фактического `cwd` для всех ролей; включить HEAD, staged/unstaged diff и содержимое untracked-файлов либо tree hash снимка. Переписать тест read-only роли на ожидание смены ключа и добавить тест двух разных dirty-содержимых с одинаковым status.

### 6. Миграция SQLite падает на базе, созданной до unique index

**Где:** `src/project-knowledge/memory-store.ts:64-104`

`CREATE UNIQUE INDEX idx_nodes_dedup` выполняется сразу. Если старая база уже содержит одинаковые `(project_id, task_id, type, content)`, инициализация падает. Репродукция со старой таблицей и двумя дублями вернула `UNIQUE constraint failed`. Текущие тесты проверяют идемпотентность только на свежей базе.

**Что исправить:** выполнить versioned migration в транзакции: удалить/объединить дубли, пересобрать FTS при необходимости, затем создать unique index и обновить `user_version`. Добавить fixture старой схемы с дублями.

### 7. Blackboard защищён только внутрипроцессным mutex

**Где:**

- `src/blackboard.ts:120-127`
- `src/blackboard.ts:136-220`
- `ui-backend/src/process-manager.service.ts:71-89`
- `src/mcp/runner-spawn.ts:47-90`

Каждый CLI-run — отдельный процесс, а backend, MCP и ручной CLI имеют независимые ограничения `hasAlive`. Два запуска из разных поверхностей могут одновременно сделать read-modify-write одного глобального `state.json`; `async-mutex` между процессами не работает. Возможны потерянные TaskRecord/StepRecord и неконсистентные отчёты.

**Что исправить:** добавить межпроцессный lock вокруг активного runner и записи state (lockfile с PID/lease либо SQLite). Минимум — атомарный global run lock в blackboard root, который одинаково используют CLI, backend и MCP. Добавить integration-тест с двумя процессами.

### 8. Git flow жёстко предполагает ветку main, хотя preflight проверяет только HEAD

**Где:**

- `src/worktree.ts:52-70`
- `src/worktree.ts:200-247`
- `src/runner.ts:1045-1055`

Репозиторий с рабочей веткой `master`, `develop` или detached HEAD проходит `rev-parse HEAD`, но затем `setupIntegration(..., base="main")` падает. Accept также всегда переключает `main`. Сообщение preflight утверждает, что ветки создаются от HEAD, что не соответствует коду.

**Что исправить:** определять и сохранять base ref при старте (`symbolic-ref --short HEAD`, с явным fallback/CLI option), создавать integration от зафиксированного SHA и использовать сохранённую target branch при accept. Добавить тест репозитория без `main`.

## P2 — важные функциональные дефекты

### 9. Позднее SSE-подключение получает exit без финального state

**Где:** `ui-backend/src/processes.controller.ts:120-131,165-176`

Live exit-handler перед `exit` читает и отправляет финальную задачу. Но если процесс завершился до подключения/reconnect, snapshot-ветка отправляет только `session`, backlog и `exit`. UI может остаться без terminal task status; accept и desktop notification зависят от `state`.

**Что исправить:** вынести единый async `sendFinalStateAndExit` и вызывать его и из live handler, и из `session.exited` snapshot. Покрыть тестом подключения после завершения.

### 10. Отчёт считает git diff в blackboard root, а не в target project

**Где:**

- `src/runner.ts:1328-1336,1373-1378`
- `src/report.ts:97-107,132-141,258-282`

`generateReport` получает только `blackboardRoot`, и этот же root используется как `cwd` для `git diff`. Для внешнего target project ветка `orch/<task>/integration` существует в другом репозитории, поэтому insertions/deletions теряются и остаются undefined.

**Что исправить:** разделить `blackboardRoot` и `gitRoot` в сигнатуре report API; добавить integration-тест с двумя разными репозиториями.

### 11. MCP get_status по taskId/list снова читает target project вместо общего blackboard

**Где:** `src/mcp/server.ts:184-213`

Ветка `clientKey` исправлена и использует `session.blackboardRoot`, но запрос по `taskId` и список используют `input.project`. Runner при этом хранит state в `ORCHESTRATOR_ROOT`. После завершения/удаления session внешний проект не сможет получить статус собственной задачи через MCP.

**Что исправить:** сделать blackboard root серверной конфигурацией, а `project` не использовать для поиска state. Если нужны несколько blackboard — хранить явное сопоставление taskId → root.

### 12. Инициализация проекта блокирует HTTP-запрос и обходится без busy/session tracking

**Где:**

- `ui-backend/src/projects.service.ts:55-76,115-126`
- `ui-backend/src/process-manager.service.ts:252-265`
- `ui-web/src/widgets/run-form/RunForm.tsx:46-58`

`POST /projects/open` ждёт полный architect workflow через `runOnce`, хотя комментарий обещает вернуть управление и polling. Операция может длиться до лимита агента, держит HTTP-запрос открытым, не появляется в `sessions`, не учитывается `hasAlive` и не может быть остановлена через UI. Параллельно можно стартовать обычную задачу, усугубляя межпроцессную гонку blackboard.

**Что исправить:** запускать init как отслеживаемую session/job и сразу возвращать 202 + clientKey/slug; использовать общий busy/lock и ограниченный ring buffer вместо неограниченного `output +=`.

## P3 — рекомендации

### 13. Уведомление о завершении подавляется у следующей задачи с тем же статусом

`ui-web/src/widgets/live-log/useExitNotification.ts:21-59` хранит только последний terminal status. После первой `done` следующая `done` в том же mounted-компоненте не уведомит пользователя. Передавать taskId/clientKey и сбрасывать guard при смене задачи.

### 14. Метрики роутинга смешивают разные роли

`src/agent-metrics.ts:55-79` агрегирует только по agent. Ошибки модели на review/plan влияют на выбор implement-исполнителя, хотя профили нагрузки и промпты разные. Хранить хотя бы `(agent, role)` либо считать метрики только по тем ролям, для которых принимается route decision.

### 15. CRUD моделей не транзакционен между models.yaml и .secrets

`ui-backend/src/models.service.ts:198-240` пишет config и secret отдельными атомарными операциями и в разном порядке для create/update. Падение между ними оставляет частичное состояние. Нужен единый commit-протокол/rollback или хранение версии конфигурации вместе с секретами в транзакционном storage.

### 16. Статус API/Ollama в Settings вводит в заблуждение

`ui-backend/src/models.service.ts:184-195` всегда возвращает `ready` для API и Ollama без проверки ключа, URL и модели; UI показывает «готов», а реальный health gate падает только при запуске. Добавить лёгкий конфигурационный статус (`missing_credentials`, `invalid_config`) и отдельную явную live health-проверку.

### 17. Modal выбора модели не имеет базовой keyboard/dialog accessibility

`ui-web/src/widgets/settings-models/AddModelModal.tsx:99-140` использует кликабельные `div` вместо radio/button, не задаёт `role="dialog"`, `aria-modal`, label association, focus trap и Escape. Это блокирует клавиатурный сценарий. Использовать нативные controls и управлять фокусом.

### 18. Документация и hygiene отстают от кода

README ссылается на отсутствующий `docs/decisions.md`, описывает GLM только через env, не объясняет реальную область действия model registry и перечисляет устаревший набор файлов/команд проверки. Кроме того, `git diff --check` падает на `ui-backend/src/models.controller.ts:132` из-за лишней пустой строки в EOF.

## Дополнение (второй проход, 2026-07-13)

Проверены места, не покрытые основным ревью: `src/lib/atomic-write.ts`, `src/worktree.ts` (candidate lifecycle), `src/project-knowledge/memory-store.ts`, `ProcessManager.runOnce/stop`. Все находки ниже — новые (в списке 1–18 их нет). Подтверждено чтением кода и точечными проверками.

### 19. `atomicWrite` не чистит временный файл при сбое (P2)

**Где:** `src/lib/atomic-write.ts:30-32`

`writeFile(tmp)` → `rename(tmp, filePath)` без `try/finally`. Если процесс падает (или `rename` бросает: EXDEV/EACCES/ENOSPC) между записью и rename, временный файл `.<name>.<hex>.tmp` остаётся сиротой в целевой директории. При многократных сбоях `.orchestrator/` (и каталог с `models.yaml`) засоряется `.state.json.*.tmp`, `.models.yaml.*.tmp`. Отдельно неприятно для `.secrets`: осиротевший `.secrets.<hex>.tmp` содержит API-ключи и, хотя создаётся с `mode`, остаётся лежать до ручной чистки.

**Что исправить:** обернуть в `try { writeFile; rename } catch { unlink(tmp).catch(()=>{}); throw }`. Опционально — при старте подчищать `.*.tmp`-сироты в blackboard root.

### 20. `atomicWrite`: `mode` подвержен umask, нет `fchmod`-гарантии (P2)

**Где:** `src/lib/atomic-write.ts:31`

`writeFile(tmp, data, { mode })` — фактические биты = `mode & ~umask`. Для секретов запрошен `0o600`, но при нестандартном umask результат может оказаться шире. Кроме того, `rename` наследует mode временного файла, поэтому при перезаписи уже существующего `.secrets` его прежние (возможно, более строгие) права молча заменяются. Файл `.secrets` создаётся, но гарантии `0600` фактически нет.

**Что исправить:** после `writeFile` явно `chmod(tmp, mode)` перед `rename` (не полагаться на umask), либо открыть fd и `fchmod`. Для секретов — проверить итоговые права в тесте.

### 21. `memory-store` открывает и закрывает соединение SQLite на каждый вызов (P3)

**Где:** `src/project-knowledge/memory-store.ts:64-105, 114-137, 153-193`; вызывающий — `src/project-knowledge/memory-extract.ts:122`

`addNode`/`searchNodes`/`listNodes` каждый раз зовут `initMemoryDb`, который открывает БД, ставит WAL и **повторно выполняет весь DDL** (CREATE TABLE/INDEX/VIRTUAL TABLE/TRIGGER), затем закрывают соединение. В `memory-extract.ts` узлы вставляются в цикле — это открытие/закрытие + полный DDL на каждый извлечённый факт. Функционально корректно (DDL идемпотентен), но это лишняя нагрузка и износ WAL при пакетной записи.

**Что исправить:** отделить одноразовую миграцию/`initMemoryDb` от рабочих операций; переиспользовать одно соединение (кэш по `dbPath` или явный `openDb()`/`close()` вокруг батча в `memory-extract`). Для батча — обернуть вставки в одну транзакцию.

### 22. `runOnce` копит вывод в неограниченную строку (P2)

**Где:** `ui-backend/src/process-manager.service.ts:253-266`

`runOnce` аккумулирует stdout+stderr в `output += c.toString()` без лимита и без `StringDecoder` (в отличие от стримингового пути, который уже починен по #11). Ревью #12 упоминает это только в контексте project init, но `runOnce` — общий метод: его также вызывают `tasks.controller.ts:58` (accept) и `projects.service.ts:117`. Длинный вывод accept/init раздувает память процесса backend, а разрезанный по границе chunk UTF-8 портит текст.

**Что исправить:** ring buffer/лимит на `output` и `StringDecoder` для обоих потоков, как в стриминговом пути. Вынести общий хелпер сборки вывода.

### 23. JSDoc и сигнатура `stop()` на одной строке (P3, hygiene)

**Где:** `ui-backend/src/process-manager.service.ts:202`

`/** ... */  stop(key: ...)` — закрывающий комментарий и объявление метода слиты в одну строку. Читается плохо и, вероятно, артефакт правки. Группируется с #18 (hygiene): вынести объявление на новую строку, прогнать форматтер по файлу.

### P1 — блокирующие проблемы

#### 24. Исправление `depends_on` сломало разбиение workflow на фазы

**Где:** `src/workflow.ts:137-152, 194-207, 507-526`

`topoLevels` теперь справедливо требует, чтобы каждая зависимость находилась в локальном `done`, но вызывается для отдельных подмножеств workflow. Например, `final` зависит от fan-out шага `build`, который намеренно не входит в `postFanOutPlain`; зависимость никогда не считается выполненной, и штатный smoke завершается ошибкой `Workflow has cyclic dependency among: final`. Та же ошибка возникает для разрешённой схемой зависимости loop/post-шага от pre-шага. Точечная репродукция: schema принимает loop step с `depends_on: [pre]`, после чего `buildLoadedWorkflow` бросает `Loop has cyclic dependency among: review`.

**Что исправить:** передавать в топологическую сортировку множество уже завершённых внешних шагов каждой фазы либо удалять только известные и допустимые межфазные зависимости. Добавить тесты на реальные workflow с `pre → fan_out → post` и `pre → loop`.

#### 25. Run lock не создаётся в чистом root, захватывается неатомарно и может не освободиться

**Где:** `src/lib/run-lock.ts:38-55`, `src/runner.ts:993-1003, 1392-1398`

`acquireRunLock` пишет `.orchestrator/.run-lock`, не создавая родительский каталог; на чистом root воспроизводится `ENOENT`. Проверка `existsSync/read` и последующая обычная `writeFileSync` образуют TOCTOU: два процесса могут одновременно решить, что lock свободен. Кроме того, lock берётся до health/preflight/createTask, а `finally` с освобождением расположен ниже: исключение до входа в этот `try` оставляет lock живого процесса.

**Что исправить:** создать blackboard directory, захватывать файл атомарно через `open(..., "wx")`, безопасно повторять попытку после удаления подтверждённо stale lock и оборачивать весь код после acquire во внешний `try/finally`. Записывать уникальный owner token и удалять lock только если владелец совпадает.

#### 26. «Глобальный» registry по-прежнему зависит от текущей директории запуска CLI

**Где:** `src/cli.ts:24-27, 139-147`, `bin/ai-task:8-14`

Пути `.env.local`, `workflows/` и `orchestratorRoot` строятся от `process.cwd()`. Wrapper находит исходники относительно собственного расположения, но cwd не меняет и root явно не передаёт. Запуск абсолютного `bin/ai-task` из временной директории показал `(no workflows/ directory)`; health/run там же читает или создаёт другой `.orchestrator`, поэтому снова возможен `base_url/api_key missing` несмотря на корректный registry проекта.

**Что исправить:** вычислять стабильный `ORCHESTRATOR_ROOT` относительно `import.meta.url`/wrapper либо обязательной переменной окружения и использовать его для env, workflows, config и blackboard. Target project хранить отдельно; cwd может быть лишь его дефолтом.

#### 27. `accept` может слить результат не в исходную ветку задачи

**Где:** `src/worktree.ts:52-74, 235-243`

Integration branch создаётся от ветки, активной при старте, но исходная base branch/SHA не сохраняется. При accept код заново определяет текущую ветку. Репродукция в temp repo: задача создана от `main`, затем checkout на `other`; `acceptTask()` успешно слил результат в `other`, а `main` не изменился.

**Что исправить:** сохранять base branch и base SHA в `TaskRecord`, принимать задачу строго в этот ref (или в явно переданную пользователем цель) и проверять ожидаемый base SHA перед merge.

#### 28. CRUD моделей всё ещё не обеспечивает заявленную транзакционность

**Где:** `ui-backend/src/models.service.ts:216-273`

В create предыдущий YAML сериализуется уже **после** `cfg.models.push(model)`, поэтому rollback записывает изменённую конфигурацию. В update секрет сохраняется до config: ошибка записи YAML оставляет новый ключ при старой модели. В remove сначала сохраняется config, затем удаляется secret: ошибка второго шага оставляет orphan secret. Пункт #15 нельзя считать закрытым.

**Что исправить:** делать snapshot до мутации, валидировать и готовить оба артефакта заранее, затем выполнять commit с полноценным rollback обоих файлов. Предпочтительно свести registry и secrets к одному транзакционному storage либо реализовать журналируемую двухфазную запись.

#### 29. Dirty fingerprint кэша имеет воспроизводимые коллизии

**Где:** `src/cache.ts:89-107`

Для untracked-файлов учитываются только первые 50 имён и первые 4096 символов каждого файла; остаток, часть бинарных данных и ошибки чтения игнорируются. Репродукция с untracked-файлом длиной 5000 символов: две версии, различающиеся только после лимита, дали одинаковый fingerprint.

**Что исправить:** потоково хешировать полное содержимое всех релевантных untracked blobs без произвольных лимитов или строить tree через временный git index. Ошибки чтения должны инвалидировать cache, а не превращаться в одинаковое состояние.

#### 30. Проверка параллельных путей не видит пересечение parent/child

**Где:** `src/workflow.ts:215-229`

`assertNonOverlappingPaths` сравнивает пути через точный `includes`, хотя ниже уже существует `pathsOverlap`, учитывающий родителя и ребёнка. Поэтому параллельные шаги с `paths: [src]` и `paths: [src/x.ts]` проходят проверку и могут одновременно менять одни файлы.

**Что исправить:** нормализовать пути и использовать `pathsOverlap` для каждой пары шагов одного DAG-level. Добавить regression test для равных, parent/child и соседних путей.

### P2 — важные проблемы

#### 31. Одинаковый step id разрешён в разных секциях workflow

**Где:** `src/workflow.ts:126-135`

Уникальность проверяется отдельно внутри `steps`, `loop.steps` и `post_steps`, но не глобально. Schema принимает одинаковый id в pre и loop, после чего `allSteps` и поиск по id становятся неоднозначными.

**Что исправить:** требовать глобально уникальные id во всём workflow либо ввести явные namespace фаз.

#### 32. UI создаёт API-модель без `model`, но backend показывает её как готовую

**Где:** `ui-web/src/widgets/settings-models/AddModelModal.tsx:76-98, 205-216`, `ui-backend/src/models.service.ts:194-198`, `src/workers/index.ts:43-48`

Create-body для API не содержит `model`, и в API-секции формы нет соответствующего input. `statusOf` считает запись готовой по base URL и secret, тогда как runtime/health для `provider: openai` требует model. Дополнительно provider доступен в edit UI, но update-body и backend schema его не изменяют — выбор молча игнорируется.

**Что исправить:** синхронизировать discriminated contracts: для OpenAI-compatible модели требовать `model`, учитывать его в status, а provider либо сделать immutable, либо полноценно валидировать и обновлять.

#### 33. Frontend не знает новые статусы моделей и подписывает ошибку как «готов»

**Где:** `ui-web/src/entities/model/index.ts:6-15`, `ui-web/src/widgets/settings-models/SettingsModels.tsx:85-90`, `ui-backend/src/models.service.ts:84-93`

Backend возвращает `missing_credentials` и `invalid_config`, но frontend union содержит только `ready/not_found/unknown`. Любой неизвестный статус отрисовывается красным цветом, но с текстом `● готов`, что вводит пользователя в заблуждение.

**Что исправить:** вынести общий/generated contract или добавить runtime parser и явные подписи для каждого backend status.

#### 34. Инициализация проекта остаётся блокирующим и нетрекаемым процессом

**Где:** `ui-backend/src/projects.service.ts:55-87, 125-136`

HTTP-запрос держится до завершения architect job; процесс не получает client key, SSE-сессию и управляемый stop. `regenerate` дополнительно не вызывает `hasAlive`, поэтому защиты от параллельного повторного запуска нет. Пункт #12 закрыт лишь частично.

**Что исправить:** возвращать `202 Accepted` с session/task id, запускать процесс через общий трекинг ProcessManager, отдавать прогресс через SSE и поддержать stop/reconnect.

#### 35. MCP-копия `runOnce` всё ещё копит неограниченный и повреждаемый вывод

**Где:** `src/mcp/runner-spawn.ts:176-190`

Backend-реализация была исправлена, но MCP продолжает делать `output += chunk.toString()` без лимита и `StringDecoder`. Большой вывод раздувает heap, а UTF-8 символ на границе chunks может быть повреждён. Пункт #22 закрыт только для одного вызывающего пути.

**Что исправить:** использовать общий capped collector/ring buffer со `StringDecoder` для stdout и stderr.

#### 36. Ollama health check не имеет таймаута

**Где:** `src/workers/health.ts` (`checkOllama`)

Запрос `/api/tags` выполняется обычным `fetch` без `AbortController`, хотя OpenAI check ограничен таймаутом. Зависший сокет может бессрочно удерживать `--health` и обязательный health gate перед запуском.

**Что исправить:** добавить тот же конфигурируемый timeout/abort и единообразно нормализовать base URL.

#### 37. Backend-дубликат atomic writer оставляет временные файлы

**Где:** `ui-backend/src/models.service.ts:21-29`

Core helper уже чистит temp в `finally`, но локальная backend-реализация не удаляет его при ошибке write/rename. Для `.secrets` это ещё и остаточный файл с ключами.

**Что исправить:** переиспользовать один проверенный atomic-write helper либо добавить гарантированную очистку temp и тест ошибки rename.

#### 38. Core schema model registry не проверяет обязательные поля по kind/provider

**Где:** `src/model-config-dto.ts:18-29`

Одна широкая schema разрешает любые optional `provider/base_url/model`. Точечная проверка показала, что API-запись без provider/base URL и Ollama-запись без model проходят `safeParse`; ошибка обнаруживается поздно в health/runtime.

**Что исправить:** использовать discriminated union, согласованный с backend create schema; дополнительно проверять уникальность ids и ссылки roles на существующие модели.

### P2 — важные проблемы

#### 43. Read-side blackboard молча трактует повреждённый state.json как пустой

**Где:** `ui-backend/src/blackboard-reader.service.ts:34-49, 19-27`

Core write-side был специально усилен (#3): повреждённый `state.json` не считается пустым, сохраняется backup и бросается явная ошибка — чтобы следующая запись не затёрла задачи. Но read-side backend делает ровно обратное: при ошибке `JSON.parse` возвращает `{ tasks: [] }`. Так как раннер переписывает `state.json` целиком неатомарно относительно внешнего читателя (или при кросс-процессной гонке #7/#25), backend может поймать «рваное» чтение и вернуть пустой список. Хуже — результат кешируется на `ttlMs=1000`, поэтому UI на секунду показывает «нет задач» и теряет активный стрим/accept. Это повторно вводит именно тот класс бага, что закрыт на write-side.

**Что исправить:** при ошибке парсинга не подменять пустым списком, а отдавать предыдущий валидный кеш (или 503/stale-флаг), логировать и не кешировать пустышку. По возможности читать через тот же атомарный контракт, что и core.

#### 44. `runApiOpenAi` не дедуплицирует повторные `read_file` — выжигает бюджет итераций

**Где:** `src/workers/runApiOpenAi.ts:105-118` (ср. `src/workers/runOllama.ts:134-147`)

`runOllama` защищён от зацикливания на чтении: подряд идущий `read_file` того же пути возвращает «(already read, see above)», не тратя итерацию. В `runApiOpenAi` эта защита отсутствует полностью — модель, застрявшая в «прочитай файл → подумай → снова прочитай тот же файл», исчерпает `maxIters` (`max_steps*8`) и завершится `budget_exhausted` вместо полезной работы. Два воркера с общим tool-loop-контрактом разошлись.

**Что исправить:** вынести общий tool-loop (dedup + исполнение + сбор сигналов) в один модуль, который используют оба воркера, либо продублировать dedup в `runApiOpenAi`. Добавить тест «модель повторяет read_file → dedup срабатывает».

#### 45. Дедуп `read_file` в `runOllama` завязан только на ключ `path`

**Где:** `src/workers/runOllama.ts:136-140` (ср. `src/workers/ollama-tools.ts:262`)

`executeTool` нормализует путь из `path | file_path | filepath | file_name`, но дедуп сравнивает только `call.args.path`. Если модель зовёт `read_file` с `file_path`/`file_name` (а `ollama-tools` специально поддерживает эти алиасы, потому что квант их выдаёт), `lastReadPath` не совпадёт и дедуп не сработает — тот же файл читается на каждой итерации, бюджет тратится впустую.

**Что исправить:** вычислять ключ дедупа той же нормализацией, что и `executeTool` (общий хелпер `resolveRawPath(call.args)`), а не по одному ключу.

#### 46. `restart` не проверяет, что исходная задача в терминальном статусе

**Где:** `ui-backend/src/tasks.controller.ts:71-92`

`restart` берёт `prompt/workflow/project` любой задачи и зовёт `start()`. Единственная защита — `hasAlive()`-busy внутри `start()`. Но нет проверки, что сама перезапускаемая задача уже завершена (`failed`/`done`/`escalated_hitl`): статус читается через кеш `BlackboardReader` (ttl 1s) и не защищён кросс-процессным локом (#7/#25). **Что исправить:** проверять `task.status` на терминальность в `restart` и отклонять иначе; полагаться на общий run lock, а не на кеш reader.
