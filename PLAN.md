# z-cc-orchestrator — план работы

Оркестрация трёх AI-CLI (Claude Pro, Codex Pro, Z.ai GLM Max) с единой точкой
входа для написания кода.

> **Кто оркестратор:** оркеструет **Node/TS-раннер** (детерминированный код —
> владеет циклом, состоянием, бюджетом). Claude, Codex и GLM — **воркеры**,
> вызываемые раннером headless на шагах воркфлоу. Claude на шаге `plan` — самый
> «умный» воркер, но всё равно под управлением раннера, а не наоборот.
> Обоснование — см. [§0. Архитектурное решение](#0-архитектурное-решение-кто-оркестратор).
>
> Стратегия: **сначала CLI, потом UI** · роутинг через **явные YAML-воркфлоу** ·
> раннер на **Node/TypeScript** (ближе к Nuxt-стеку, упрощает этап UI).
> Фундамент архитектуры — паттерны из
> [`p3nchan/cc-orchestrator`](https://github.com/p3nchan/cc-orchestrator);
> референс YAML-пайплайнов и UI — [`hoangsonww/AI-Agents-Orchestrator`](https://github.com/hoangsonww/AI-Agents-Orchestrator).

---

## 0. Архитектурное решение: кто оркестратор

Было две возможные архитектуры — фиксируем **B**.

| | A: Claude-as-orchestrator | **B: Node-раннер оркеструет ✅** |
|---|---|---|
| Кто читает YAML | Claude через bash-tool | **Node-раннер** |
| Кто вызывает воркеров | Claude сам дёргает `run-*.sh` | **Раннер вызывает CLI headless** |
| Роль `src/runner.*` | минимальна / не нужна | **ядро системы** |
| Claude на plan/review | он же оркестратор | **вызывается как воркер** |
| Бюджет/circuit-breaker | «просьба к модели» (не гарантия) | **гарантия в коде** |

**Почему B:** выбраны явные YAML-воркфлоу + resilience (budget caps,
circuit breaker, checkpoint). Это детерминированная механика — её должен
исполнять код, а не языковая модель. Если YAML читает Claude, бюджет-контроль
превращается в просьбу к модели, а не в гарантию. Поэтому **раннер владеет
циклом, состоянием и бюджетом; Claude/Codex/GLM — воркеры**. Claude остаётся
«мозгом» на шаге `plan`, но не управляет циклом.

Практическое следствие: `bin/ai-task` → зовёт **Node-раннер** → раннер читает
`workflow.yaml` → для каждого шага формирует task-envelope → запускает нужный
воркер (`run-claude` / `run-codex` / `run-glm`) headless → собирает результат в
blackboard → следующий шаг.

## 1. Концепция

```
                    ТЫ  (одна точка входа: ai-task "…")
                         │
                         ▼
             ┌───────────────────────────────┐
             │   Node/TS РАННЕР (ОРКЕСТРАТОР) │  читает workflow.yaml ·
             │   src/runner.ts               │  владеет циклом, состоянием,
             │                               │  бюджетом · пишет blackboard ·
             │                               │  мержит worktrees
             └───────────┬───────────────────┘
                         │  на каждом шаге: envelope → запуск воркера headless
        ┌────────────────┼──────────────────────────┐
        ▼                ▼                           ▼
 ┌──────────────┐ ┌──────────────┐          ┌──────────────────┐
 │   codex      │ │   claude     │          │  claude + GLM    │
 │  (воркер)    │ │  (воркер)    │          │  (воркер)        │
 │  OpenAI      │ │  Anthropic   │          │  Z.ai            │
 │  имплемент,  │ │  plan, UI/UX,│          │  массовый        │
 │  тесты,      │ │  тонкое      │          │  boilerplate,    │
 │  рефакторинг │ │  ревью       │          │  рутина (дёшево) │
 └──────┬───────┘ └──────┬───────┘          └────────┬─────────┘
        └────────────────┴───────────────────────────┘
                         ▼
      git worktrees целевого проекта  +  FILE BLACKBOARD (.orchestrator/)
      (единственная надёжная шина между разными моделями — файлы на диске)
```

Раннер — единственный, кто держит состояние. Воркеры **stateless**: получают
envelope, делают работу, отдают результат, умирают.

### Роли и семьи моделей (для кросс-семейного ревью)

| Воркер | Бинарник | Семья | Зона ответственности |
|---|---|---|---|
| **Claude** | `claude` | **Anthropic** | `plan`, UI/UX, тонкое ревью, финальная приёмка |
| **Codex** | `codex` | **OpenAI** | Имплементация, рефакторинг, генерация тестов (сильный sandbox) |
| **GLM Max** | `claude` + env | **Z.ai** | Массовый boilerplate, рутина, дешёвый объём (щедрые лимиты Max) |

**Три семьи, а не бинарника.** GLM запускается бинарником `claude`, но это
**отдельная семья Z.ai** — для правил ревью считается чужой по отношению к
Anthropic-Claude.

**Правило кросс-семейного ревью:** код, написанный одной семьёй, ревьюит
**другая** (самопроверка слепа на ~64%). Валидные пары ревьюера:

| Код написал | Кто может ревьюить |
|---|---|
| Codex (OpenAI) | Claude (Anthropic) **или** GLM (Z.ai) |
| Claude (Anthropic) | Codex (OpenAI) **или** GLM (Z.ai) |
| GLM (Z.ai) | Claude (Anthropic) **или** Codex (OpenAI) |

Раннер на шаге `review` **обязан** выбрать воркера из семьи, отличной от той,
что писала код (см. §3.4).

## 2. Ключевой технический факт про подписки

Все три — **локальные CLI с авторизацией по подписке** (не API-ключ с оплатой
за токены):

- **Claude Pro** → бинарник `claude` (Claude Code), логин по подписке.
- **Codex Pro** → бинарник `codex` (OpenAI), логин по подписке.
- **Z.ai GLM Coding Max (Monthly Plan)** → подключается **через тот же
  `claude`**, подменой окружения: `ANTHROPIC_BASE_URL` + ключ Z.ai. То есть это
  второй профиль `claude`, а не отдельный инструмент. Тариф — помесячный.

  > ⚠️ Это **допущение**, а не факт. Оно проверяется в **Этапе 0.0** (gate)
  > до любой другой работы — см. §3.

Следствие для архитектуры (**если gate пройден**): два из трёх агентов — один
бинарник `claude` с разным env. Удобно: один механизм запуска, разные профили.
**Если gate НЕ пройден** — GLM становится третьим отдельным адаптером (свой
CLI/API-клиент), и тезис «два из одного» отменяется; на структуру §4 это влияет
только реализацией `run-glm`, остальная архитектура (раннер-оркестратор) не
меняется.

- [ ] `2.4` **Task-envelope** — единый JSON от раннера воркеру. Поля:

      ```jsonc
      {
        "id": "T-042",
        "agent": "codex",           // claude | codex | glm
        "family": "openai",         // anthropic | openai | zai — для правил ревью
        "role": "implement",        // plan|implement|review|refine|fix|final
        "prompt": "…",
        "target_paths": ["src/…"],  // ограничивает область работы
        "context": "…|null",        // вывод предыдущего шага, подставляемый раннером:
                                    //   digest checkpoint (после обрыва, 4.3)
                                    //   | замечания review (→ fix)
                                    //   | план подзадач (plan → implement)
                                    //   | null для первого шага

          "wall_time_sec": 1500,    // общий таймбокс шага
          "max_steps": 3,           // число диспатчей/ретраев
          "max_session_min": 25     // только для codex: лимит одной сессии
        },
        "effort": "medium"          // low|medium|high|xhigh (нативный effort CLI)
      }
      ```
- [ ] `2.5` **Сигналы успеха воркера** (раннер проверяет ПОСЛЕ каждого запуска):
  - **Codex** (3 сигнала, все обязательны): exit 0 **и** `turn.completed` в JSONL
    **и** sidecar-файл результата на диске. Один сигнал в одиночку врёт.
  - **Claude / GLM** (свой набор): exit 0 **и** непустой last-message **и**
    ожидаемые `target_paths` реально изменены (`git status` в worktree непустой,
    если шаг предполагал правки).
  - Любой невыполненный сигнал → structured error event (4.4), не «тихий успех».

### Этап 3 — YAML-воркфлоу (роутинг)  ·  ~1–2 дня

- [x] `3.1` Схема `workflows/*.yaml`: список шагов, на каждом — `agent`,
      `role`, `effort`, `budget`, `depends_on`. Плюс опциональные `loop` и
      `post_steps` (см. ниже).
- [x] `3.2` Встроенные воркфлоу. **Жёсткое соответствие ролей и агентов:**
  `plan`=claude · `implement`/`fix`/`refine`=glm · `review`=codex · `final`=claude.
  Кросс-семейность автоматически соблюдена (Z.ai пишет → OpenAI ревьюит).
  - `default`   : `glm(implement) → codex(review)`
  - `quick`     : `glm(implement)` — ⚠️ **ревью опущено осознанно**; только для
                  тривиальной рутины. Результат **не идёт в main без ручной
                  проверки** (раннер помечает ветку как `needs-human-review`).
  - `thorough`  : `loop[claude(plan) → glm(implement) → codex(review)]` + post-loop `claude(final)`
                  — цикл пока APPROVE (лимит 3), затем финальная приёмка.
  - `ui`        : `glm(implement UI) → codex(review)` — кросс-семейность Z.ai→OpenAI.
  - `boilerplate`: `glm(generate) → codex(review)` — GLM(Z.ai) → Codex(OpenAI) ✅
  - `agentic`   : `loop[claude(plan) → glm(implement) → codex(review)]` —
                  агентский цикл: claude планирует, glm пишет, codex ревьюит,
                  повтор пока codex не даст APPROVE (лимит 3, потом HITL).
- [x] `3.3` **Раннер (ядро)**: парсит YAML → строит граф шагов по `depends_on` →
      для каждого шага формирует envelope → запускает воркера → проверяет сигналы
      успеха (2.5) → пишет результат/состояние в blackboard → следующий шаг.
      Владеет бюджетом и циклом целиком (см. §0). Поддерживает `loop`:
      тело исполняется по кругам, выход — по вердикту `exit_on`-шага
      (APPROVE → выход, REJECT → HITL, REQUEST_CHANGES → следующий круг).

**Loop-конструкция в YAML** (PLAN §3.1, расширение):
```yaml
steps: []            # линейные шаги ДО цикла (DAG)
loop:
  steps:             # тело цикла (исполняется последовательно каждый круг)
    - { id: plan, agent: claude, role: plan, ... }
    - { id: implement, agent: glm, role: implement, depends_on: [plan], ... }
    - { id: review, agent: codex, role: review, depends_on: [implement], ... }
  exit_on: review    # чей вердикт проверяем (роль review или final)
  max_iterations: 3  # лимит кругов
  on_exhausted: hitl # hitl | accept (если лимит исчерпан без APPROVE)
post_steps:          # линейные шаги ПОСЛЕ цикла (DAG)
  - { id: final, agent: claude, role: final, ... }
```
Условие выхода: `APPROVE`/`ACCEPT` → выход, `REJECT` → HITL,
`REQUEST_CHANGES` → следующий круг (контекст review передаётся в plan).
Лимит исчерпан → `on_exhausted` (hitl = эскалация, accept = берём как есть).
Каждая итерация пишет результаты с суффиксом `#N` (не перетирает историю).
- [ ] `3.4` **Enforcement кросс-семейности**: перед шагом `review`/`final` раннер
      смотрит семью автора кода предыдущего шага и **выбирает ревьюера из другой
      семьи** (таблица пар в §1). Если YAML задаёт ревьюера той же семьи —
      раннер это отклоняет (ошибка валидации воркфлоу), кроме явного
      `allow_same_family: true` на шаге.

### Этап 4 — Защита от сюрпризов (resilience)  ·  ~1 день

- [ ] `4.1` Budget caps: раннер стережёт `budget` из envelope (§2.4). Превышение
      `wall_time_sec`/`max_steps` → шаг прерывается, не «просьба к модели».
- [ ] `4.2` Circuit breaker: N подряд неуспехов на воркере → воркер помечается
      сгоревшим, шаг эскалируется в HITL, ретраи прекращаются. (Dead-letter-queue
      — опционально на этом же этапе; пока просто HITL, см. §6.)
- [ ] `4.3` **Checkpoint & resume — ответственность РАННЕРА, не модели**:
  - Раннер даёт Codex-шагу таймбокс `max_session_min ≤ 25` (после `/compact`
    сессия может «умереть», `resume` вернёт мёртвую).
  - По завершению/обрыву раннер читает вывод воркера и **сам пишет
    `.orchestrator/checkpoints/<task>-<n>.json`** (digest сделанного + что дальше).
    Codex сам digest надёжно не пишет — не полагаемся на его `/compact`.
  - Свежая сессия подхватывает digest через поле `context` в новом envelope (§2.4).
- [ ] `4.4` Structured error events: любой невыполненный сигнал успеха → событие
      в `log/` с причиной. Loud failure > quiet success.
- [ ] `4.5` HITL-эскалация: воркер не уверен / конфликт merge / сгорел circuit
      breaker → раннер останавливается и спрашивает тебя (не автопочинка).

### Этап 4.5 — Worktrees и слияние результатов  ·  ~полдня

- [ ] `4.5.1` **Именование**: на задачу — интеграционная ветка
      `orch/<task-id>/integration`; каждому воркеру — worktree на ветке
      `orch/<task-id>/<agent>` (напр. `orch/T-042/codex`).
- [ ] `4.5.2` **Параллельность только на непересекающихся `target_paths`.**
      Если у шагов пересекаются пути — раннер исполняет их **последовательно**.
- [ ] `4.5.3` **Слияние делает раннер**, последовательно: fast-forward /
      `merge --no-ff` веток воркеров в `orch/<task-id>/integration`. Раннер
      **дожидается завершения всех воркеров шага**, затем мержит их ветки в
      `integration` по одной (по порядку завершения). Запуск merge до того, как
      все воркеры шага закончили, запрещён — это и устраняет гонки.
- [ ] `4.5.4` **Конфликт merge → НЕ автоматический разбор.** Раннер
      останавливается, пишет конфликт в blackboard и эскалирует (HITL, 4.5).
- [ ] `4.5.5` В `main` целевого проекта результат попадает только после приёмки
      (шаг `final` / ручное подтверждение). Раннер НЕ пишет в `main` сам: человек
      запускает `ai-task --accept <task>` (триггер приёмки), после чего раннер
      делает `merge --ff` из `orch/<task-id>/integration` в `main` целевого проекта.
      Без `--accept` интеграционная ветка остаётся живой.

## 5. Принятые ограничения (из боевого опыта cc-orchestrator)

- **Файлы — единственная шина** между разными моделями (переживает краши).
- **≤25 минут** на один Codex-запуск; дальше — checkpoint и свежая сессия.
- **3 параллельных воркера — потолок** (4+ конфликтует с окном лимитов).
- **Кросс-семейное ревью** обязательно (самопроверка слепа на ~64%).
- **Codex headless:** в 0.142.5 флаг `-a never` **устарел** — вместо него
  `-s workspace-write` + `--skip-git-repo-check` (подробнее в
  `docs/versions.md`); для `npm install` — `-c sandbox_permissions='["network-access"]'`,
  а не выключать sandbox целиком.
- **Успех Codex = три сигнала** (exit 0 + `turn.completed` + sidecar-файл);
  один сигнал в одиночку врёт.
- **Бюджет — не в долларах** (подписки): `wall_time_sec` + `max_steps`
  (+ `max_session_min ≤ 25` для Codex). Раннер стережёт, circuit breaker страхует.
- **Оркеструет код, не модель** (§0): раннер владеет циклом/состоянием/бюджетом.
- **Три семьи** (Anthropic / OpenAI / Z.ai); GLM = Z.ai несмотря на бинарник `claude`.
- **Checkpoint пишет раннер**, не модель; свежая сессия получает его через `context`.
- **Merge — последовательный, раннером**; конфликт → HITL, не автопочинка.
- **В `main` пишет только приёмка**, не оркестратор.
- **Review/final запускаются в integration-worktree**, не в основном репо —
  иначе reviewer не видит код implementer-а (баг, выявленный E2E). implement/
  refine/fix — в собственных worktree-ах на ветках агентов.
- **Loud failure > quiet success** — сбои делаем шумными намеренно.

## 6. Открытые вопросы (уточнить по ходу)

- [ ] Точный base URL Z.ai GLM Coding Plan → **проверяется в Этапе 0.0 (gate)**.
- [ ] Нужен ли dead-letter-queue сразу или на этапе 4 достаточно retry+breaker.
- [ ] Параметры `N` для circuit breaker (сколько неуспехов = сгорел) — подобрать на практике.

**Решено (было под вопросом — теперь зафиксировано):**
- **Оркестратор — Node/TS-раннер**, не Claude (§0, вариант B).
- **GLM-совместимость — блокирующий gate (Этап 0.0)**, не «вопрос по ходу».
- **Три семьи** Anthropic/OpenAI/Z.ai; GLM = Z.ai для правил ревью (§1).
- **Единица бюджета** — время + шаги (+ сессия для Codex), не доллары (§2.4).
- **Запуск раннера** — TypeScript через `tsx`, без билд-шага в dev (§4).
- **Checkpoint пишет раннер** (§4.3); **merge — последовательный раннером** (§4.5).
- **`quick`** без ревью — осознанно, не в `main` без ручной проверки (§3.2).
- Тариф Z.ai — **GLM Coding Max, Monthly Plan** (помесячно).
- Язык раннера — **Node/TypeScript**.
