# Tasks

## Project init: асинхронная отслеживаемая сессия

- **Статус:** backlog
- **Источник:** finding #34 из `review-2026-07-13.md`
- **Приоритет:** P2

### Проблема

`open`/`regenerate` держат HTTP-запрос до завершения architect job. У процесса нет устойчивого идентификатора сессии, повторного подключения к прогрессу и полноценной остановки со стороны UI. Минимальная проверка `hasAlive()` в `regenerate()` закрывает гонку параллельных запусков, но не устраняет блокирующий HTTP.

### Что сделать

- Перевести `open` и `regenerate` на запуск через отслеживаемую сессию `ProcessManager`.
- Возвращать `202 Accepted` с `clientKey`/идентификатором сессии сразу после старта.
- Передавать прогресс и терминальное состояние через SSE.
- Добавить остановку активной инициализации.
- Поддержать reconnect: новый клиент должен получить последнее известное состояние и продолжить чтение событий.
- Обновить UI: состояния запуска, выполнения, ошибки, отмены и повторного подключения.
- Исключить параллельные init/regenerate для одного проекта.

### Критерии приёмки

- HTTP-запрос запуска не ждёт завершения architect job и отвечает `202`.
- Повторный запуск для того же проекта во время активной сессии отклоняется предсказуемым `409` либо возвращает существующую сессию.
- Клиент видит накопленный вывод и итоговый статус после переподключения.
- Stop завершает дочерний процесс и переводит сессию в терминальное состояние `cancelled`/`stopped`.
- Ошибка запуска или выполнения отражается в SSE и доступна после reconnect.
- Для backend и UI добавлены тесты happy path, duplicate start, stop, failure и reconnect.

### Вне текущего минимального фикса

В текущем наборе исправлений достаточно добавить `hasAlive()` в `regenerate()`. Полная async-реализация выполняется этой отдельной задачей.
