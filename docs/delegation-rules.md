# Правила делегирования (для воркеров)

> Это **инструкции воркерам** (промпты ролей), а не правила диспатча.
> Диспатч живёт в `workflows/*.yaml` + раннере (PLAN §5.2). Раннер решает,
> какого агента вызвать на каком шаге; эти правила описывают, **как** воркер
> должен вести себя в своей роли.

## Общие правила для всех воркеров

1. **Работай только в своём worktree.** Не трогай файлы вне `target_paths`
   (если заданы). Раннер ограничил область — уважируй это.
2. **Делай коммиты атомарно.** Каждый логический кусок работы — отдельный
   коммит в своей ветке `orch/<task-id>/<agent>`.
3. **Не запускай долгие процессы** (>5 мин) без явной необходимости. Бюджет
   шага ограничен (`wall_time_sec`), раннер убьёт тебя по таймбоксу.
4. **Если не уверен — останавливайся.** Лучше отдать неполный результат с
   пометкой, чем сжечь лимит на догадки. Раннер эскалирует в HITL.
5. **Выводи summary в конце.** Последнее сообщение (last-message) — это то,
   что раннер положит в blackboard как результат шага.

## Роли

### `plan` (обычно Claude)
- Декомпозируй задачу в список подзадач с `target_paths`.
- Не пиши код — только план. Формат: пронумерованный список шагов.
- Указывай, какой воркер最适合 какую подзадачу (codex для тяжёлой
  имплементации, glm для boilerplate, claude для UI).

### `implement` (codex / glm / claude)
- Пиши код по плану из `envelope.context` (если есть).
- Соблюдай стиль существующего кода в проекте.
- Запускай тесты, если они есть. Красные тесты = провал шага.
- Коммить после каждого логического блока.

### `review` (семья, отличная от автора)
- Читай diff из worktree автора (`envelope.context` содержит его вывод).
- Проверяй: корректность, безопасность, стиль, edge-cases.
- Возвращай **список замечаний** (пронумерованный, с путями файлов).
- Если всё ок — явное «LGTM, замечаний нет».

### `refine` / `fix` (обычно тот же агент, что и implement)
- Исправляй замечания из `envelope.context` (вывод review).
- Не переписывай то, что не отмечено в замечаниях — минимизируй diff.

### `final` (обычно Claude)
- Финальная приёмка: тесты проходят, замечания закрыты, diff чистый.
- Возвращай вердикт: `ACCEPT` или `REJECT <причина>`.

## Кросс-семейность (раннер enforcement)

Раннер отклонит воркфлоу, где review той же семьи, что implement —
кроме случаев с `allow_same_family: true` на шаге. Не пытайся это обойти
в промпте; если нужен same-family review (редкость), укажи флаг в YAML.
